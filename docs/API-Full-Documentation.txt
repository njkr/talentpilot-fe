TalentPilot API
Frontend Story Flow, Backend Architecture & Live API Test Rep

Part 1 — What TalentPilot Is
TalentPilot takes a candidate's resume and a job posting and turns them into everything a real job application needs: an ATS-style compatibility score, concrete rewrite suggestions (fabrication-checked in code, not just prompted against), a tailored cover letter, interview questions grounded in the candidate's actual history, a researched briefing on the company, a salary range, and a focused learning plan for the skill gaps that matter. Everything after upload is produced by a single asynchronous pipeline run — one credit-metered action that fans out into twelve coordinated steps.
The eight sprints, in one table
Sprint
Theme
What it added
1
Auth & Accounts
Registration, OTP email verification, login/refresh token rotation with theft detection, password reset, sessions.
2
Resumes, Profiles & Storage
S3/R2/MinIO-backed uploads, magic-byte file validation, profile completeness, plan limits.
3
AI Core & Resume Parsing
The shared AiService gateway (Structured Outputs, budget guard, pricing, prompt versioning) and AI-driven resume-to-JSON extraction.
4
Job Descriptions, Embeddings & Matching
JD analysis, pgvector-backed semantic embeddings, keyword coverage matching.
5 & 6
Workspaces, Pipeline Backbone & ATS Scoring
The credit ledger, the BullMQ-driven step pipeline (DAG execution, SSE progress, idempotent retries, proportional refunds), and the ATS scoring engine as its first real step.
7
Optimisation, Versions & Cover Letter
The resume optimiser with an in-code fabrication guard, append-only resume version history, and AI-generated cover letters.
8
Parallel Career-Prep Generators
Interview questions with practice-mode feedback, a capped learning roadmap, Tavily-grounded company research (globally cached), and salary estimation — all running concurrently with the scoring branch.


High-level shape of the system
Two Node.js processes share one Postgres database and one Redis instance:
The API process (NestJS + Express) — handles every HTTP request. Stateless; horizontally scalable.
The worker process — a separate NestFactory.createApplicationContext() app with no HTTP listener. Consumes BullMQ queues (resumes, pipeline, emails) and is the ONLY process that ever calls OpenAI or Tavily for pipeline work. This keeps the API process's boot fast and its dependency graph free of heavy AI/embeddings code it doesn't need for orchestration.
Postgres holds every domain table (30+ tables across the 8 sprints) plus pgvector embeddings.
Redis backs BullMQ queues, pub/sub for live progress (SSE), and single-use SSE auth tickets.
MinIO (S3-compatible) stores the actual resume/JD files; the database only stores a key reference.

2.1. Create an account
The sign-up screen. The frontend posts email + password. The account is created unverified, and — the moment registration succeeds, not on verification — a `user.registered` event silently grants the new account SIGNUP_CREDIT_GRANT (100) credits via the credits ledger, and queues a 6-digit OTP email.

2.2. Verify email
The user enters the 6-digit code from their inbox. On success the endpoint returns an access token AND sets an httpOnly refresh cookie (`tp_rt`, scoped to /api/v1/auth) — verification doubles as first login. The code is hashed with argon2 (not sha256) specifically because it's only a 6-digit space (10^6 possibilities); a fast hash would make an offline brute force of a leaked database trivial.
API call:  POST /auth/verify-email
Example request body:

  "code": "482913"

Refresh tokens rotate on every use; if the SAME token is ever replayed after rotation, the backend treats it as theft and revokes the entire device family.

2.14a — What actually happened when we ran this live (a genuine failure and recovery)
In this test run, one required step — generate_cover_letter — actually failed on the first attempt: the model's draft tripped the placeholder guard (a real-code check, not just a prompt instruction) and the run finished with status: failed, having refunded 4 of the 21 credits (the exact combined weight of the failed step and everything still blocked behind it). Part 3 — Backend Architecture, In Detail
3.1 — Process topology
The backend is two independently-deployable NestJS applications sharing one Postgres database and one Redis instance, plus MinIO/S3 for file bytes:
API process (src/main.ts → AppModule): every HTTP route. Bootstrapped with NestFactory.create(), Swagger docs at /api/docs, a global ValidationPipe (whitelist + forbidNonWhitelisted), a global ClassSerializerInterceptor (honors @Exclude on passwordHash), a global response-shaping TransformInterceptor, and a global AllExceptionsFilter.
Worker process (src/main.worker.ts → WorkerModule): bootstrapped with NestFactory.createApplicationContext() — no HTTP listener at all. Consumes three BullMQ queues: emails, resumes, pipeline. This is the ONLY process that imports AiModule, EmbeddingsModule, or any Tavily-touching code — a deliberate DI-graph boundary enforced by which modules each process's root module imports, not just convention.
A NestJS module can be imported into BOTH processes when it exposes both a controller (API-reachable) and a service the worker calls directly from a pipeline step — CoverLetterModule, InterviewModule, and AtsModule are all built this way (a controller for the API process's synchronous/on-demand endpoints, plus the same service reused inside a pipeline step). The controller class is harmless when the worker's createApplicationContext() loads it too: without an HTTP adapter bound, its routes are simply never exposed anywhere.
3.2 — The response envelope and error model
Every 2xx response from the API process is shaped identically by a global interceptor:
{
  "success": true,
  "data": { /* the actual payload */ },
  "meta": { "requestId": "...", "timestamp": "...", "nextCursor"?: "...", "hasMore"?: true }
}


Every error response, thrown from anywhere, is caught by one global AllExceptionsFilter and shaped identically:
{
  "success": false,
  "error": { "code": "INSUFFICIENT_CREDITS", "message": "...", "details"?: {...}, "fields"?: {...} },
  "meta": { "requestId": "...", "timestamp": "..." }
}


The `code` values are a closed enum (ErrorCode in common/exceptions/app.exception.ts) mapped to a fixed HTTP status (STATUS table in the same file). A small catalogue module (common/problems.ts) exposes one factory function per named failure — Problems.insufficientCredits(required, balance), Problems.jdNotReady(status), etc. — so every service throws the same shape for the same failure instead of ad-hoc NestJS exceptions scattered through the codebase. As of Sprint 8 this catalogue holds 40+ named errors across every domain.
3.3 — Auth & security model (Sprint 1)
Passwords: argon2id (memoryCost 64 MiB, timeCost 3, parallelism 4) — OWASP-aligned, not bcrypt.
Access tokens: short-lived JWT (default 15 min), payload {sub, role, ver}. `ver` is the user's tokenVersion column — bumping it (on password reset, or a detected refresh-token replay) instantly invalidates every access token already issued, even ones whose own expiry hasn't passed, since the guard checks ver against the current DB value on every request.
Refresh tokens: opaque, NOT a JWT — format "<uuid>.<32-byte base64url secret>", stored as sha256(secret) only (a stolen database yields no usable tokens), delivered as an httpOnly cookie scoped to /api/v1/auth. Rotate on every use.
Theft detection: if a refresh token is presented AFTER it's already been rotated away, that's not a race — it's replay of a token that shouldn't exist anymore — and the entire device family is revoked, not just that token.
Concurrent-refresh race (two tabs refreshing at once) is explicitly NOT theft: the loser gets a soft TOKEN_SUPERSEDED and should retry with its current token.
Timing-safe auth: invalid email and invalid password return byte-identical bodies in equalized wall-clock time (PasswordService.fakeVerify() burns the same CPU as a real verify when the user doesn't exist) — no user-enumeration oracle.
OTP codes: 6 digits, argon2-hashed (not sha256) specifically because the search space is only 10^6 — a fast hash would make a leaked-database offline brute force instant.
Password-reset tokens: 256-bit random, sha256-hashed (safe at that entropy), single-use, 30-minute TTL.
3.4 — Storage (Sprint 2)
One StorageService abstraction talks to any S3-compatible backend — real AWS S3, Cloudflare R2, or local MinIO — switched purely by environment variables (S3_ENDPOINT/S3_FORCE_PATH_STYLE/S3_SERVER_SIDE_ENCRYPTION). Uploaded files are never trusted by extension or browser-reported Content-Type — FileValidatorService reads the actual magic bytes (%PDF- for PDF; the ZIP signature PK\x03\x04 plus a check for the literal string word/document.xml inside for DOCX, which also rejects a renamed .xlsx/.pptx/.jar/.apk). Downloads are served via short-lived signed URLs (SIGNED_URL_TTL_SEC), never proxied through the API process.
3.5 — The AI Gateway (Sprint 3)
Every AI-touching feature in the whole product — resume parsing, JD analysis, ATS grading, resume optimisation, cover letters, interview questions/feedback, company synthesis, salary estimation — calls exactly one method: AiService.complete<T>(opts). That single choke point is what makes the following guarantees uniform product-wide instead of re-implemented per feature:
Budget guard: a global AND a per-user daily USD cap (AI_GLOBAL_DAILY_BUDGET_USD / AI_USER_DAILY_BUDGET_USD), checked BEFORE the call, plus a kill switch (AI_KILL_SWITCH) that stops all AI instantly.
Structured Outputs: every prompt has a Zod schema (src/ai/schemas/*.schema.ts) turned into an OpenAI response_format via zodResponseFormat() — the model literally cannot return a shape that doesn't match, eliminating a whole class of "the AI returned something we couldn't parse" bugs.
Prompt versioning: PromptTemplate rows in Postgres, not hardcoded strings — a prompt can be edited, versioned, and rolled back without a deploy. Exactly one version per key is is_active at a time.
Retry classification: AiError has a closed type union (rate_limited, provider_down, invalid_output, context_too_long, budget_exceeded, content_filtered, unknown) computed from the REAL OpenAI SDK error classes (instanceof checks against RateLimitError etc.), not string/duck-typing — only invalid_output gets one repair retry; the rest fail immediately or are already retried inside the SDK.
Cost tracking: every attempt (success or failure) logs one token_usage row with exact prompt/completion/cached token counts and a computed cost_usd (6 decimal places — a single 4o-mini call can cost $0.0009, and that precision matters once you're doing 100k calls).
Prompt-injection defence: every prompt's system template explicitly marks user-supplied content (resume text, JD text, search results) as UNTRUSTED DATA inside XML-ish tags, with an explicit instruction never to obey directives found inside them.
3.6 — Job descriptions, embeddings & matching (Sprint 4)
JDs are analysed INLINE (not queued) since it's a single fast AI call; content-hash deduped per user so pasting the same text twice is free.
Embeddings are stored in Postgres via pgvector (vector(1536), text-embedding-3-small) — NOT a separate vector database. Chunked SECTION-AWARE, not by a fixed token window: a naive sliding window can split "Senior Engineer at Acme, 2020–2023" from its own achievement bullets, orphaning them with no idea which role they belonged to.
JD chunking is one chunk PER REQUIREMENT (not per paragraph) — matching asks "does the resume satisfy requirement X", so each requirement needs its own query vector; chunking by paragraph would blur five requirements into one meaningless vector.
Embeddings are content-hashed per chunk and reused across re-runs — editing one bullet re-embeds ONLY that chunk, not the whole resume.
Keyword matching is a separate, deterministic-ish pass (semantic similarity via embeddings is one signal; literal/canonical keyword presence is a second, independent signal) — the ATS score in Sprint 6 blends both rather than relying on either alone.

3.7 — Credits: an append-only ledger, not a mutable balance
credits_ledger has no "balance" column. A user's balance is always SUM(amount) for that user — positive rows are grants/refunds, negative rows are debits. Two reasons this matters:
Self-auditing: "why does this user have 79 credits" is always answerable by reading history, never a mystery number.
Race safety: two concurrent debits on a single mutable `balance` column can both read the same stale value and both succeed (a classic lost-update). An append-only ledger has no single row to SELECT ... FOR UPDATE on instead — so debitWithin() takes a Postgres transaction-scoped advisory lock (pg_advisory_xact_lock(hashtext(userId))) before computing SUM() and inserting the negative row, serialising concurrent debits for the SAME user across different DB connections, auto-released on commit or rollback.
Confirmed live in this session's own testing: a run that failed partway refunded exactly the combined credit-weight of the failed step and everything blocked behind it (verified against the ledger's raw rows, not just the API's summary field), and a subsequent successful retry did not re-debit anything.
3.8 — The pipeline: workspaces, runs, and the 12-step DAG (Sprints 5–8)
A workspace pairs one resume with one job description. Calling POST /workspaces/{id}/analyze does three things atomically inside one transaction: creates a pipeline_runs row, debits credits, and is protected from ever having two ACTIVE runs for the same workspace by a database-level partial unique index — CREATE UNIQUE INDEX one_active_run_per_workspace ON pipeline_runs (workspace_id) WHERE status IN ('queued','running') — not just an application-level check, which a race between two near-simultaneous requests could slip past. The BullMQ job is enqueued only AFTER that transaction commits, so the worker can never pick up a run row that isn't visible yet.

Progress weights sum to exactly 100; credit weights sum to exactly 21 — both asserted at worker boot (StepRegistry.assertValid()), so a typo can never silently ship.

StepRunner — the execution engine
Wave-based scheduling: each iteration computes every step whose dependencies are satisfied, runs them all concurrently (bounded by p-limit(3)), then recomputes the next wave. This — not a continuous per-step scheduler — is the actual mechanism behind "the three JD-only steps run alongside the scoring branch": they become ready in the SAME wave as generate_embeddings, well before score_ats even starts several waves later.
Idempotent by construction: before running a step, StepRunner checks whether a pipeline_steps row for (runId, stepName) already has status='completed' — if so it's skipped, unconditionally. This is what makes a crashed-and-retried run safe: it resumes instead of restarting, and never double-charges or duplicates AI calls for work already done.
Per-step retry: up to 3 attempts, but ONLY for errors classified as retryable (currently AI_PROVIDER_UNAVAILABLE) — exponential backoff with jitter between attempts.
Optional-step semantics: a step with `required = false` (research_company, estimate_salary) failing marks the run partial, never failed, and — critically — a dependency on a failed-but-optional step is treated as "resolved enough to proceed" by the scheduler, not as blocking. Without that specific rule, finalize (which depends on every step, optional ones included) would be transitively blocked by ANY optional failure and the run would incorrectly end up failed instead of partial — a real bug found and fixed during this project by testing the failure path live rather than trusting the design on paper.
Proportional refunds: on any non-completed outcome, refunded = round(creditsCharged × (sum of creditWeight for failed+blocked steps) / (sum of creditWeight for all steps)). Confirmed live: a run where generate_cover_letter (weight 3) and its sole dependent finalize (weight 1) were the only casualties refunded round(21 × 4/21) = 4 credits, exactly.
Real per-step cost: every AiService call already tags its token_usage row with (runId, stepName); StepRunner sums that back onto the pipeline_steps.cost_usd column when a step finishes (success OR failure — a step can spend real money and still fail afterward). A run's total_cost_usd is the sum across all steps.
Live progress (SSE)
The worker publishes step-lifecycle events onto Redis pub/sub (channel run:<id>); the API process subscribes and forwards them over Server-Sent Events using Nest's native @Sse() decorator — which already sets the correct text/event-stream, keep-alive, and no-buffering headers, so nothing extra is needed there. Two SEPARATE ioredis connections are required (one publish, one subscribe) because a client in Redis subscriber mode can only run subscribe/unsubscribe commands. Authentication uses a 60-second single-use Redis-backed ticket instead of a bearer token, because EventSource cannot set request headers at all — putting a real access token in the query string would leak it into server and proxy logs.
Failure recovery: the run janitor
A cron job (@Cron(EVERY_5_MINUTES)) sweeps for runs stuck at status='queued' for more than 5 minutes with no corresponding BullMQ job — the narrow crash window between a transaction committing and the enqueue call actually landing — and re-enqueues them under a deterministic rescue job ID.
3.9 — The fabrication guard (Sprint 7) — why it exists in code, not just the prompt
The resume optimiser and cover-letter generator both carry an explicit, absolute no-invention rule in their system prompts. That rule measurably reduces fabrication. It does not eliminate it, because the model isn't lying on purpose — it pattern-matches "strong resume bullets have metrics" and supplies one, with no awareness that the number doesn't exist anywhere in the source. The cost of that failure mode is not a bad UX: it's a candidate confidently discussing a project they never did, in a real interview, because a tool told them it was on their resume.
FabricationGuardService therefore re-verifies every model-proposed suggestion in code before it is ever shown to a user:
Numbers: every percentage/currency/count/multiplier in the proposed text must already appear in the source resume in some recognisable form.
Years: every 19xx/20xx token must appear in the source.
Organisations: two-or-more consecutive capitalised words are checked against the resume's OWN parsed employer/institution/issuer/project list — not generic NER, which is less reliable than data the parser already extracted.
Credentials: words like "certified", "PhD", "MBA" must already appear in the source — adding one is a categorically different kind of lie than rephrasing a sentence.
A suggestion that fails any check is dropped silently and logged at WARN level naming the specific violation — the user never sees a rejected suggestion, and this session's own testing produced real, live examples: an invented "45%, 2M users" claim, an invented "Goldman Sachs" employer, and an invented "Certified" credential were all caught and dropped in practice, not just in unit tests.
The SAME tension shows up in cover letters via a simpler, narrower check: any output containing an unfilled [bracketed placeholder] is rejected outright rather than shown, on the reasoning that a letter with "[Company Name]" in it is worse than no letter — the user might actually send it. This session's live testing hit that rejection for real (not a staged test) on two separate generations, confirming the guard fires under normal production conditions and not just in a lab reproduction.
3.10 — Resume version history (Sprint 7)
Append-only: applying suggestions or restoring an old version always creates a NEW resume_versions row and a NEW set of resume_sections rows at the next version number — the previous version's rows are never mutated or deleted.
Why: the ATS report that scored v1 refers to v1's actual text. Editing v1 in place would silently make every historical report describe content that no longer exists, and the user could never get back to their original upload.
Staleness protection: every AiSuggestion stores a sha256 hash of the exact bullet text it targeted at generation time. If the user hand-edits that bullet before accepting the suggestion, the hash no longer matches and the suggestion is refused (marked stale) rather than silently discarding the user's edit — confirmed live in this session.
One nuance worth knowing for a frontend: GET /resumes/{id}/versions only returns EXPLICIT version-creation events (an apply or a restore) — the very first upload (v1) never gets its own resume_versions row unless something later creates v2+. A version-history UI should synthesize a "v1 — original upload" entry from the resume's own createdAt if the list doesn't already contain one.

5.3 — Findings
One real product behaviour was observed live that's worth calling out explicitly, plus two minor, non-financial reporting nuances noticed while reading raw ledger/DB state during the test:
Finding 1 — The fabrication/placeholder guard genuinely fires in production use (by design, working correctly)
Across this session's cumulative live testing, cover-letter generation tripped the unfilled-placeholder guard on more than one real occasion — including once inside this very test's full pipeline run. This is not a flaw: it is the guard doing exactly what it is for. The observable product consequence is that generate_cover_letter (a REQUIRED step) failing turns the whole run status=failed rather than the softer status=partial, with a proportional credit refund — and the retry endpoint is the correct, working recovery path, confirmed live in this report. Teams shipping this product should expect a non-trivial baseline rate of first-attempt cover-letter rejections and should treat "failed, retry available" as an expected steady-state outcome for this step, not an incident.
Finding 2 — pipeline_runs.creditsRefunded is overwritten, not accumulated, across a retry
When a run fails and is refunded (say 4 credits), then successfully retried, the run row's own creditsRefunded field is reset to 0 on the successful finalise — but the EARLIER +4 refund ledger entry is never reversed, so the user's actual wallet balance is correct and untouched. This is confirmed by direct ledger inspection in this report: the user's real balance reflects a +100 grant, a -21 charge, and a +4 refund that remains permanently in their favour, exactly as it should. The only inaccuracy is cosmetic — a run summary that, after a fail-then-succeed cycle, under-reports its own refund history. Recommendation: if this run-level summary field is surfaced to users, either accumulate it across attempts or drop it in favour of always reading the ledger directly for that run's reference_id.
Finding 3 — GET /resumes/:id/versions does not include an implicit "version 1"
The endpoint only returns rows that were created by an explicit action (apply-suggestions or restore). A brand-new resume that has never had a suggestion applied or a version restored will return an EMPTY list, even though the resume itself is obviously "at version 1". A version-history screen should treat an empty response as "still on the original upload" and synthesize a v1 entry from the resume's own createdAt, rather than treating an empty list as an error state.
5.4 — Cost & performance, observed
Full 12-step pipeline run (fresh test account, first attempt): 84% progress reached before the cover-letter failure at roughly 35 seconds elapsed; the retried run completed shortly after.
A separate full successful run earlier in this project's testing (same pipeline, different workspace) completed end-to-end in under 45 seconds and cost $0.027 in real OpenAI spend, most of it (~72%) in the single gpt-4o optimize_resume call — matching the design intent that only the quality-critical rewriting step uses the larger model, everything else uses gpt-4o-mini or embeddings.
Company research demonstrated its 7-day global cache hitting on a second lookup for the same normalised company name, at zero additional Tavily/AI cost — confirmed via fromCache: true and a matching zero row in token_usage for that step.

6.1 — Frontend story additions
Six new things a user (or an admin) can now do, continuing directly from where Part 2 left off.
6.1.1. Download a generated document
From a completed workspace, the user requests a resume PDF, resume DOCX, cover letter (either format), or a full report PDF. The request returns immediately with status "queued" — the actual rendering (Puppeteer for PDFs, the docx package for Word files) happens on the worker. The frontend polls GET .../documents/:docId until status flips to "ready", then calls the download endpoint for a short-lived signed S3 URL. If the user accepts new suggestions or regenerates their cover letter AFTER a document was built, that document silently flips to "stale" — the frontend should treat stale the same as "not ready yet" and prompt a fresh request rather than serving an out-of-date file.
6.1.2. Get notified when something finishes
A bell icon shows an unread count. Analyses that complete (or fail/partial) while the user is away from the SSE progress screen still produce a notification — a domain event fires from StepRunner independently of the live progress stream, so closing the tab never means missing the result. Preferences are opt-OUT: a user can silence emails for specific notification types without losing the in-app entry.
6.1.3. Upgrade to a paid plan
From a billing screen, choosing Pro or Ultimate calls the checkout endpoint and redirects the browser to Stripe's hosted Checkout page — card details never touch this API. On success, Stripe calls back via webhook (not via the redirect itself, which is not trustworthy for granting access) to activate the subscription and refill monthly credits. A failed card on renewal moves the subscription to "past_due" and emails the user, but doesn't immediately revoke access — Stripe's own retry schedule gets a real chance before anything downgrades.
6.1.4. View the dashboard
One screen answers "where do I stand": credit balance, plan and its limits, resume/workspace counts against those limits, the most recent workspaces and their statuses, and the unread notification count — all in one request, cached for 30 seconds so a refresh storm does not turn into six times the database load per hit.
6.1.5. (Admin only) Inspect a run, manage the dead-letter queue, activate a prompt
A small, separately-gated surface for operators: pull up any run's full step-by-step history for debugging, browse and retry jobs that permanently failed in any queue, see AI cost broken down by feature/day/user, and flip which prompt template version is live for a given key — all without a deploy. Every mutating action here is written to the audit log with actorType "admin".
6.1.6. Request your data, or delete your account
A user can request a full data export (delivered as a download link once a background job finishes assembling it) or delete their account. Deletion is a soft delete — it's immediate for login purposes (every session is revoked on the spot) but the account is only hard-purged, along with every table that references it, 30 days later.
6.2 — Backend architecture additions
6.2.1 — Document generation (Sprint 9)
A new GeneratedDocument row tracks each requested file: its type, S3 key once rendered, the resume/cover-letter version it was built from (for staleness), and a status machine (queued → generating → ready | stale | failed). DOCX generation follows strict ATS-safe rules enforced in code, not just convention: no tables, text boxes, multi-column layout, headers/footers, or images — a single linear column of paragraphs, using Word's tab-stop feature (not table cells) for right-aligned dates, since ATS parsers frequently drop table content entirely. PDF rendering reuses ONE Puppeteer browser instance across jobs (launching Chromium costs 1-2 seconds — doing it per job would make generation feel broken) but recycles the whole browser every 50 pages, since Chromium's steady memory leak would otherwise eventually OOM-kill the worker. Handlebars templates share layout via a registered partial; a resume-shaped object built once from ResumeSection rows feeds the same PDF template a live preview would use, so what the user saw is exactly what they download.
6.2.2 — In-app notifications & pipeline events (Sprint 9)
StepRunner now emits genuine domain events (run.completed / run.failed) via EventEmitter2 — distinct from the pre-existing Redis pub/sub ProgressBus used for live SSE progress, which only reaches a client with an open connection. A PipelineNotificationListener reacts to these events and writes a Notification row (plus an email, unless the user opted out for that type), wrapped so a notification failure can never fail the pipeline job itself. Accepting suggestions, restoring a resume version, or regenerating a cover letter each mark any already-built document derived from the old version as stale, scoped by workspace (a resume can be attached to more than one workspace).
6.2.3 — Payments (Sprint 10)
Plan, Subscription, and WebhookEvent are new tables; the existing credit ledger (Sprint 5's append-only design) was extended with a referenceType column and new reasons (monthly_refill, purchase, admin_adjust) rather than replaced with a second, competing ledger. Stripe webhook signature verification needs the exact raw request bytes, which Nest's default JSON body parser destroys before a handler ever sees them — main.ts now boots with bodyParser:false and manually wires raw-body parsing for the one webhook path, JSON for everything else. Idempotency is handled by inserting the event's id first and catching a Postgres unique-constraint violation (23505) as "already processed", rather than an exists-then-insert check that would race under concurrent delivery. A subscription's own lastEventAt timestamp guards against Stripe's at-least-once, any-order webhook delivery: an event older than the last one applied is a no-op, not a regression. A daily cron independently re-derives every active subscription's status directly from Stripe's API, as a safety net for the rare webhook that never arrives.
6.2.4 — Real plan limits (Sprint 10)
The Sprint 2 PlanLimitService stub — hardcoded plan limits with a planFor() that always returned "free" and a comment reading "later sprint: read the user's actual subscription" — is now exactly that: it reads the user's Subscription row (a canceled subscription falls back to the free plan's limits, a past_due one still counts as its paid plan during Stripe's grace period) and looks limits up from the Plan table. The public method signatures are unchanged, so every existing caller kept working untouched; a previously-missing workspace-creation limit check was added at the same time, since the stub's own maxWorkspaces field had never actually been enforced.
6.2.5 — Dashboard (Sprint 11)
DashboardService fetches credit balance, plan/subscription, resume and workspace counts, the five most recently updated workspaces, and unread notification count in a single Promise.all — none of the six depends on another's result — then caches the assembled result in Redis for 30 seconds per user.
6.2.6 — Admin (Sprint 11)
AdminGuard is a deliberate double gate: role === "admin" is not sufficient on its own — the user's email must ALSO appear in an env-controlled ADMIN_ALLOWED_EMAILS allowlist. A bug in role assignment, or a compromised admin account, cannot alone unlock the panel; an attacker needs both. Behind that gate: a run inspector (the run row plus every PipelineStep, including each step's outputRef — added in Sprint 7 specifically to let an inspector jump from a step to what it produced), dead-letter-queue browsing/retry across all four BullMQ queues, an AI cost breakdown by feature/day/top-spending-user straight from token_usage, and prompt-version activation reusing PromptsService's existing transactional deactivate-then-activate method unchanged.
6.2.7 — Audit log (Sprint 11)
AuditLog gained a resourceId column (it previously had no way to say which row an action was about). The ad-hoc write pattern AuthListener already used inline is now a shared AuditService with a log() that never throws — an audit failure must never break the caller's real action — and a filterable, cursor-paginated list() backing the admin audit viewer the module's own original comment anticipated ("the seam for a future admin-facing view audit log endpoint").
6.2.8 — GDPR (Sprint 11)
Data export is queued, not synchronous: a worker process collects the user's profile, resumes, workspaces, ATS reports, cover letters, credit ledger and more into one JSON file, uploads it to S3, and notifies the user with a signed link once it exists. The daily hard-purge job runs 30 days after UsersService.softDelete() and does real, careful cleanup rather than a bare DELETE FROM users: every Sprint 5+ table (ats_reports, pipeline_runs/pipeline_steps, ai_suggestions, cover_letters, and more) stores plain uuid columns with no real foreign key — an established, deliberate app-level-ownership design — so each is deleted explicitly, scoped by the user's workspace ids, before the User row itself. One extra orphan-risk table was found and handled during this work: resume_versions has no real foreign key to resumes either (unlike resume_sections, which does cascade correctly), so it is deleted by resumeId before the purge proceeds. Any active Stripe subscription is canceled and every S3 object under the user's prefix is removed; a Stripe API failure during cancellation is logged and swallowed rather than blocking the purge, since the local database rows are the actual source of truth for compliance, not a third party's availability.

6.5 — Two real bugs this round, caught only by actually booting the app
Bug 1 — Stripe's esModuleInterop trap
import Stripe from 'stripe' compiles cleanly and passes every Jest test in this project (Jest's jest.mock('stripe', ...) replaces the whole module, sidestepping the problem entirely) — but throws "stripe_1.default is not a constructor" the instant the real app tries to construct PaymentsService or GdprService. This project's tsconfig has esModuleInterop off, and the stripe package is a TypeScript export= module with no .default — a default import silently binds to undefined at runtime. Fixed in both services with import Stripe = require('stripe'), the same class of issue the codebase had already hit once before with cookie-parser in main.ts.
Bug 2 — migration:generate wanted to destroy every stored embedding
TypeORM's migration diff against the live database included, alongside the genuinely new Sprint 9-11 tables, a DROP COLUMN and re-ADD of embeddings.embedding as character varying — silently changing it from vector(1536) and destroying every stored pgvector embedding, because the entity's TypeScript type (varchar, deliberately insert:false/update:false since the column is raw-SQL-managed) doesn't match what the introspector expects for a pgvector column. Caught by reading the generated migration before running it, rather than trusting the generator output blindly; the final applied migration contains only the genuine schema additions, hand-verified against a second diff that confirmed zero remaining drift.
Both bugs share a lesson this whole project has leaned on from Sprint 1 onward: a clean compile and a green test suite are necessary, not sufficient — they verify units in isolation, not the real module graph, the real database, or a real third-party SDK's actual runtime shape.
6.6 — Second verification pass: three real gaps closed, two false positives ruled out
A follow-up verification report raised C1-C6 and M1/M2/M5 again, plus eleven new items (M3-M11) and several smaller findings. Re-checked against the actual codebase rather than applied blindly: C1-C6, M1, M2, and M5 were already fixed (the report was auditing this document's OWN stale pre-fix §2/§5 captures, not current code) — no changes were needed there. Of the new items, three were real and were fixed; the rest (M3, M6-M9) remain open by choice, scoped to a later pass.
6.6.1 — Health endpoints (M4)
GET /health/live and GET /health/ready, backed by @nestjs/terminus. Liveness deliberately checks NO dependency — a Postgres/Redis outage should page someone, not trigger a container-restart storm on every replica; that's what readiness is for. Readiness pings Postgres (TypeOrmHealthIndicator) and Redis (a new RedisHealthIndicator, using its own dedicated ioredis connection so a health check can never contend with real traffic) and returns Terminus's own response shape — not the usual {success,data,meta} envelope, since orchestrators expect a plain body. Both routes are @Public(), bypassing the global JWT guard, since load balancers and container orchestrators have no bearer token to send.
6.6.2 — Idempotency-Key on checkout (M10)
POST /payments/checkout now requires a unique Idempotency-Key header, same as the existing POST /workspaces/:id/analyze. The key is passed straight through as Stripe's OWN idempotency key on the API call, rather than tracked in a local table — Stripe is already the system of record for checkout sessions, and its API natively deduplicates a repeated request with the same key for 24 hours. A double-clicked "Upgrade" button can no longer create two Checkout sessions.
6.6.3 — Missed monthly-refill safety net (M11)
The daily reconciliation cron (PaymentsService.reconcileAll) previously only corrected a subscription's status/period drift against Stripe. It had no way to notice that a single missed invoice.payment_succeeded webhook left a user's subscription status perfectly correct while that month's credits were silently never granted — a different failure mode from status drift, and one the reconciliation job was not actually checking for. Subscription gained a last_refill_at column (migration SubscriptionRefillTracking); reconcileAll now compares it against the Stripe subscription's current_period_start and grants the missing refill if the last one predates the current period.
6.6.4 — Billing policy decision, made explicit
The report flagged that re-analysing an unchanged resume/JD pair still charges the full flat ANALYZE_CREDIT_COST even though parse_resume/parse_jd get skipped (their combined credit weight is refunded from nothing, since skipping isn't failing). This was a genuine product decision, not a bug: kept as a flat fee — "analyze" is priced as one action — and documented explicitly at the constant's definition so it reads as a decision, not an oversight, the next time someone finds the same discrepancy.
